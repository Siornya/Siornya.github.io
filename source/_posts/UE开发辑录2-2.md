## 什么是 Gameplay Tags

在游戏开发中，我们经常需要描述一个对象“是什么”或者“正处于什么状态”。例如：是否死亡？是否解锁？是否被减速？

但随着玩法增加，这种做法很快会产生大量互相耦合的字段和判断。枚举也只能表示一组互斥状态，并不适合表达“角色同时中毒、燃烧并且无法移动”。

Gameplay Tags 是 UE 提供的一套**全局注册、具有层级关系的`FName`标签系统**。一个标签本质上是类似下面这样的名字：

```text
Character.State.Debuff.Burn
Ability.Movement.Dash
```

`FGameplayTag`的比较是效率更高的`FName`等式检查，而不是字符串比较，适合高频调用。

Gameplay Tags 通常应在初始化阶段完成注册。虽然`UGameplayTagsManager::AddNativeGameplayTag`可以在引擎启动后调用，但是可能破坏 Fast Replication 的索引一致性。所以不应该在游戏运行时创建新的标签。

## 设计游戏中的 Gameplay Tags

**Tag 的使用**

Gameplay Tags可以用来替换`enum/bool/string`，但我们应该避免“万物皆Tag”。Tag通常只回答“有或没有”，所以我们可以用它来表示分类、能力、状态和事件。生命值、持续时间、层数等连续或带数量的数据，仍然应该存放在普通变量或专门的状态结构中。

**Tag 的命名**

标签的命名非常重要，我们知道标签是具有层级的，此处上级标签应该在语义上覆盖所有下级标签。此外，标签还是全局范围生效的，所以标签应该有且只有一个语义，不能在不同的子系统中被解释成不同的含义。

`.` 分隔出了标签的层级。`Character.State.Debuff.Burn` 不仅能精确匹配自身，也能匹配它的上级标签从 `Character.State.Debuff` 到 `Character`。因此上层系统也可以询问“它是否具有任意角色状态”，而不需要知道所有具体状态。

**Tag 的管理**

谁拥有并管理标签同样重要，我们可以在多种地方创建标签容器。比如在某个子系统中创建`FGameplayTagContainer`，当然也可以在全局创建。

尽管存档系统可以筛选标签或只序列化部分 Container，但全局 Container 仍会混淆所有权、生命周期、复制范围和持久化策略。所以不建议只使用一个全局 Container 来保存所有 Tag。

但也没必要每个子系统分别保存标签，这样会导致子系统之间的复杂依赖，而且会让标签查询变得更加复杂。我们可以根据生命周期，标签使用，存档和复制策略来定义`FGameplayTagContainer`，既可以在一个子系统内使用多个，也可以让多个子系统共用一个。

## 启用与配置

把`GameplayTags`模块依赖加入`Build.cs``PublicDependencyModuleNames`。如果只在`Private/`目录下的头文件中使用，也可以考虑加入`PrivateDependencyModuleNames`。

然后我们需要先添加标签，在编辑器中打开 `Project Settings -> Project -> Gameplay Tags`，启用 `Import Tags From Config`，再通过 `Manage Gameplay Tags` 添加标签。

默认标签会保存在 `Config/DefaultGameplayTags.ini`，可以直接修改文件添加标签。如果 Tag 数量较多，也可以在 `Config/Tags` 下按系统建立多个 Tag Source，例如 `CharacterTags.ini`、`ItemTags.ini`。

```ini
[/Script/GameplayTags.GameplayTagsList]
GameplayTagList=(Tag="Character.State.Dead",DevComment="角色已经死亡")
GameplayTagList=(Tag="Character.State.Debuff.Stunned",DevComment="角色被眩晕")
GameplayTagList=(Tag="Ability.Movement.Dash",DevComment="冲刺能力")
```

也可以通过创建行结构为`GameplayTagTableRow`的 Data Table 来导入标签，只要把数据表添加到`Gameplay Tag Table List`里即可。

### 在 C++ 中声明原生标签

除了在配置文件中添加标签，还可以通过C++代码定义。使用`UE_DECLARE_GAMEPLAY_TAG_EXTERN`和`UE_DEFINE_GAMEPLAY_TAG`等宏在C++代码中声明和定义标签，方便在代码中直接引用。

C++中可以通过查找全局字典取得已经注册的标签。但这是一种直接但不推荐的做法，因为如果有拼写错误，只能在运行时被发现。`const FGameplayTag DeadTag = FGameplayTag::RequestGameplayTag(FName("Player.State.Dead"));`

原生标签能集中管理名称，在模块加载时完成注册，也能让编译器帮助检查变量名。

首先在`.h`中声明标签：`UE_DECLARE_GAMEPLAY_TAG_EXTERN(X_Y_Z);`。

然后在`.cpp`中定义标签：`UE_DEFINE_GAMEPLAY_TAG(X_Y_Z, "X.Y.Z");`，如果需要给Tag添加注释，也可以使用`UE_DEFINE_GAMEPLAY_TAG_COMMENT(X_Y_Z, "X.Y.Z", "comment");`

只在一个`.cpp`文件内部使用的标签可以通过`UE_DEFINE_GAMEPLAY_TAG_STATIC`定义，不需要在头文件中使用`DECLARE`宏声明。

**使标签跨模块可用**

`UE_DECLARE_GAMEPLAY_TAG_EXTERN`当前本质上只是声明一个`extern FNativeGameplayTag`，不会自动附带模块的导出宏。如果需要在其他模块使用，就需要在标签的声明宏前添加`MODULE_API`把这个符号导出。

另外，使用这个标签的模块还要在对应的`[MODULE].Build.cs`里添加对定义标签模块的依赖。

## FGameplayTag 与 FGameplayTagContainer

`FGameplayTag`表示单个标签，`FGameplayTagContainer`表示一组不重复的标签。实际对象通常同时拥有多个状态，因此大多数时候应该保存 Container，并借此进行添加、删除和查询：

```cpp
#include "GameplayTagContainer.h"

UPROPERTY(EditAnywhere, BlueprintReadOnly, Category = "Gameplay Tags")
FGameplayTagContainer OwnedTags;

// 此处 Tag 是 FGameplayTag 类型变量

OwnedTags.AddTag(Tag);
OwnedTags.RemoveTag(Tag);

if (OwnedTags.HasTag(Tag)) {
    // 死亡标签存在
}
```

`HasTag` 默认进行层级匹配，而 `HasTagExact` 只进行精确匹配。例如 Container 中有 `Player.State.Dead` 时：

| 查询 | 结果 |
| --- | --- |
| `HasTag(Player.State)` | `true` |
| `HasTagExact(Player.State)` | `false` |
| `HasTagExact(Player.State.Dead)` | `true` |

Container 之间还可以使用：

- `HasAny`：至少匹配查询集合中的一个标签
- `HasAll`：匹配查询集合中的全部标签
- `HasAnyExact`、`HasAllExact`：对应的精确匹配版本
- `AppendTags`：合并另一个 Container
- `RemoveTags`：批量删除标签

需要注意，空查询集合传给 `HasAny` 会返回 `false`，传给 `HasAll` 会返回 `true`，因为“空集合中的所有条件”确实都得到了满足。

## 使用 Gameplay Tag Query 表达复杂条件

简单判断可以直接使用 `HasTag`，但数据驱动的技能、物品或者交互条件经常需要更复杂的逻辑，例如：

> 角色拥有冲刺能力，并且没有死亡或眩晕状态。

这类条件适合使用 `FGameplayTagQuery`。它能组合 `Any`、`All`、`None` 三种标签表达式，也能继续嵌套子表达式。

```cpp
using namespace DenebGameplayTags;

FGameplayTagQueryExpression HasDash;
HasDash.AllTagsMatch()
    .AddTag(Ability_Movement_Dash);

FGameplayTagQueryExpression IsNotBlocked;
IsNotBlocked.NoTagsMatch()
    .AddTag(Character_State_Dead)
    .AddTag(Character_State_Debuff_Stunned);

FGameplayTagQueryExpression RootExpression;
RootExpression.AllExprMatch()
    .AddExpr(HasDash)
    .AddExpr(IsNotBlocked);

FGameplayTagQuery CanDashQuery;
CanDashQuery.BuildQuery(RootExpression);

if (CanDashQuery.Matches(OwnedTags))
{
    StartDash();
}
```

如果 Query 通过 `UPROPERTY(EditAnywhere)` 暴露给编辑器，策划可以直接使用可视化的 Query 编辑器组合条件，不需要修改 C++：

```cpp
UPROPERTY(EditAnywhere, Category = "Requirements")
FGameplayTagQuery ActivationRequirements;
```

因此，**固定且高频的底层判断使用原生标签，变化频繁的玩法条件使用可编辑 Query**，通常是比较清晰的分工。

## 让不同对象以统一方式提供标签

如果武器、角色和可交互物都有各自的标签字段，调用方不应该为了读取标签而依次 Cast。UE 提供了 `IGameplayTagAssetInterface` 来统一这个过程。

```cpp
// TaggedActor.h
#pragma once

#include "CoreMinimal.h"
#include "GameFramework/Actor.h"
#include "GameplayTagAssetInterface.h"
#include "TaggedActor.generated.h"

UCLASS()
class DENEB_API ATaggedActor : public AActor, public IGameplayTagAssetInterface
{
    GENERATED_BODY()

public:
    virtual void GetOwnedGameplayTags(
        FGameplayTagContainer& TagContainer
    ) const override;

private:
    UPROPERTY(EditAnywhere, Category = "Gameplay Tags")
    FGameplayTagContainer OwnedTags;
};
```

```cpp
// TaggedActor.cpp
void ATaggedActor::GetOwnedGameplayTags(
    FGameplayTagContainer& TagContainer
) const
{
    TagContainer = OwnedTags;
}
```

使用时只依赖接口：

```cpp
FGameplayTagContainer TargetTags;

if (const IGameplayTagAssetInterface* TagInterface =
        Cast<IGameplayTagAssetInterface>(TargetActor))
{
    TagInterface->GetOwnedGameplayTags(TargetTags);
}
```

需要注意，接口只规定如何**读取**标签，不会替你保存、修改、复制标签，也不会自动产生标签变化事件。

## 修改入口与事件

如果其他系统需要响应标签变化，不应把 Container 暴露出去任意修改，而应该集中通过函数添加和删除标签，并在真正发生变化时广播事件：

```cpp
DECLARE_MULTICAST_DELEGATE_TwoParams(
    FOnOwnedTagChanged,
    FGameplayTag,
    bool // 是否已添加
);

FOnOwnedTagChanged OnOwnedTagChanged;

bool ATaggedActor::AddOwnedTag(FGameplayTag Tag)
{
    if (!Tag.IsValid() || OwnedTags.HasTagExact(Tag))
    {
        return false;
    }

    OwnedTags.AddTag(Tag);
    OnOwnedTagChanged.Broadcast(Tag, true);
    return true;
}

bool ATaggedActor::RemoveOwnedTag(FGameplayTag Tag)
{
    if (!OwnedTags.RemoveTag(Tag))
    {
        return false;
    }

    OnOwnedTagChanged.Broadcast(Tag, false);
    return true;
}
```

普通的 `FGameplayTagContainer` 没有内置的变化监听机制。Gameplay Ability System 中的 `UAbilitySystemComponent` 另有 `RegisterGameplayTagEvent`，不要把两者混为一谈。

如果同一种状态可能由多个来源提供，例如装备和 Buff 都赋予 `Character.State.Invisible`，单纯的 Set 语义会导致其中一个来源移除标签时把另一个来源的效果也删掉。这时应该为标签维护引用计数，只有计数从 `0` 变为 `1` 或从 `1` 变为 `0` 时才广播可见状态变化。GAS 的标签计数同样解决了这类问题。

## 网络复制

`FGameplayTag` 和 `FGameplayTagContainer` 支持网络序列化，但把它们放进 Actor 并不会自动复制。Actor 本身需要启用复制，属性也需要使用普通的属性复制声明：

```cpp
// TaggedActor.h
public:
    ATaggedActor();

    virtual void GetLifetimeReplicatedProps(
        TArray<FLifetimeProperty>& OutLifetimeProps
    ) const override;

private:
    UPROPERTY(
        EditAnywhere,
        BlueprintReadOnly,
        ReplicatedUsing = OnRep_OwnedTags,
        Category = "Gameplay Tags",
        meta = (AllowPrivateAccess = "true")
    )
    FGameplayTagContainer OwnedTags;

    UFUNCTION()
    void OnRep_OwnedTags(const FGameplayTagContainer& PreviousTags);
```

```cpp
// TaggedActor.cpp
#include "Net/UnrealNetwork.h"

ATaggedActor::ATaggedActor()
{
    bReplicates = true;
}

void ATaggedActor::GetLifetimeReplicatedProps(
    TArray<FLifetimeProperty>& OutLifetimeProps
) const
{
    Super::GetLifetimeReplicatedProps(OutLifetimeProps);
    DOREPLIFETIME(ATaggedActor, OwnedTags);
}

void ATaggedActor::OnRep_OwnedTags(
    const FGameplayTagContainer& PreviousTags
)
{
    for (const FGameplayTag& Tag : OwnedTags)
    {
        if (!PreviousTags.HasTagExact(Tag))
        {
            OnOwnedTagChanged.Broadcast(Tag, true);
        }
    }

    for (const FGameplayTag& Tag : PreviousTags)
    {
        if (!OwnedTags.HasTagExact(Tag))
        {
            OnOwnedTagChanged.Broadcast(Tag, false);
        }
    }
}
```

RepNotify 可以接收与被复制属性相同类型的参数，此时 UE 会传入属性复制前的值。上面的 `OnRep_OwnedTags` 据此找出客户端新增和移除的显式标签，并复用本地变化事件。标签的权威修改应该发生在服务器；客户端只根据复制结果更新表现，不应在 `OnRep_OwnedTags` 中反向修改权威状态。

项目设置中的 `Fast Replication` 会用双方共同的 Tag Net Index 代替完整名称，能减少带宽，但服务器和客户端必须使用完全一致的标签表。运行过程中动态注册原生标签也可能让这个索引失效，因此核心标签应在模块加载阶段完成注册。

如果只需要本地分类，不要为了“以后可能用到”就复制整个标签集合。对于频繁变化且数量很大的状态，应进一步评估 GAS、Fast Array 或更专门的同步结构。

## 标签的命名与维护

在建立标签系统时建议先约定少量稳定的根节点，例如：

```text
Character.State.*
Item.Type.*
Ability.*
Input.*
GameplayEvent.*
UI.*
```

重命名已经投入使用的标签时，通过编辑器的 Gameplay Tag Manager 操作，让 UE 生成 Redirect；不要直接删除旧名字再添加新名字。Redirect 最终类似：

```ini
+GameplayTagRedirects=(OldTagName="Character.State.Stun",NewTagName="Character.State.Debuff.Stunned")
```

提交代码时也要一并提交 `Config` 中的标签源和 Redirect，否则其他成员或打包环境中可能找不到标签。

## 常见误区

1. **把 Tag 当成字符串。** 应该集中声明原生标签或从编辑器属性中选择，避免在业务代码里散落 `RequestGameplayTag`。
2. **把所有数据都塞进 Tag。** `Damage.Fire.20` 不是一个好的标签；`Damage.Type.Fire` 配合数值 `20` 更合适。
3. **误解父子关系。** Container 持有子标签不代表它显式持有父标签，是否匹配父级取决于使用的是层级匹配还是 Exact 匹配。
4. **直接公开修改 Container。** 这会绕过事件、引用计数、存档和网络权威规则。
5. **无规划地扩展根节点。** 标签树不是越深越好，层级应该服务于实际查询。
6. **认为 Gameplay Tags 等于 GAS。** Gameplay Tags 是独立模块，可以单独使用；GAS 只是在此基础上提供了标签计数、事件、效果和网络预测等更完整的能力。
